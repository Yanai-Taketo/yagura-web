要　旨

Yagura（やぐら）は、Windows Server 上で単一の Windows サービスとして動作する、オープンソース（Apache License 2.0）の syslog 集約サーバである。ネットワーク機器・サーバのログを一元的に受信・保存し、Web ブラウザから検索・可視化できる。ライセンス費用は不要で、Linux サーバの併設も要しない。本資料では、製品概要、システム構成と要件、セキュリティ設計、ライセンス上の取り扱い、導入プロセス、サポート体制を、導入判断に必要な範囲でまとめる。

導入の背景と課題

ネットワーク機器（ファイアウォール、スイッチ、無線 AP、UPS 等）およびサーバのログを各機器内に留めたままにすると、次の課題が生じる。

  • 障害対応の遅延 — 機器ごとに管理画面を確認する必要があり、複数機器にまたがる事象の相関把握が困難
  • ログの喪失 — 機器内蔵ログは容量が小さく、再起動・上書きで消失する。機器障害時には当該機器のログ自体が参照不能となる
  • 証跡の不備 — 設定変更・認証失敗等の記録が保全されず、監査・インシデント調査の基礎資料を欠く

syslog による集約はこれらへの標準的な対策であるが、従来の選択肢は、ライセンス費用を要する商用製品か、Linux サーバの構築・運用スキルを前提とする Linux 系 OSS に限られていた。Windows 中心の運用体制を持つ組織にとって、いずれも導入障壁が存在する。Yagura は、この間隙を埋める Windows ネイティブの OSS として開発されている。選定観点の詳細な比較は別稿を参照。

システム構成と要件

構成

受信・解析・保存・閲覧の全機能が単一の Windows サービスとして動作する。追加のミドルウェア、Web サーバ、データベースサーバの事前構築は不要である（SQL Server の利用は任意）。MSI の実行により、サービス登録、Windows ファイアウォール規則の作成、内蔵データベースの用意までが完了する。

リソース

必要なディスク容量は受信量と保持期間に依存する。一般的なネットワーク機器のログのみであれば所要量は小さい（試算方法は別稿「ディスク容量の見積もり」を参照）。保持期間は既定 30 日の自動削除により管理される。

セキュリティ設計

設計方針

Yagura は「既定を軽く、強化を明示的に（opt-in）」という方針を採る。導入直後の状態は管理された社内ネットワークでの利用を前提とした最小構成であり、要件に応じて保護機能を段階的に有効化する。

利用の前提（開発元が定める利用上の掟）

  • 管理された社内ネットワーク（信頼できる網の内側）での利用を前提とすること
  • 既定の受信は平文（udp・tcp 514）であることを理解のうえ運用すること
  • 閲覧 UI は既定で LAN 内に読み取り専用・無認証で公開されることを理解すること
  • インターネットに露出する機器、接続者を統制できないネットワークには設置しないこと

有効化できる保護機能（いずれも opt-in）

  • 受信経路の暗号化 — syslog over TLS（tcp/6514・RFC 5425）
  • 閲覧 UI のアクセス制御 — Windows 統合認証 + Active Directory グループマッピングにより、「閲覧」「管理」の役割で利用者を制限
  • 閲覧 UI の HTTPS 化 — 同一ポートのまま HTTPS へ切替（平文の待ち受けは残らない）。証明書は Windows 証明書ストアから選択し、サーバ名との不一致は保存前に検査。期限切れ時も平文へはフォールバックしない
  • 管理 UI の保護 — 既定は loopback 限定。リモート公開する場合は Windows 統合認証（AD/Kerberos）または独自 ID/パスワード認証を要し、HTTPS が必須となる（fail-closed）
  • 資格情報の保護 — SQL Server 接続パスワードは Windows DPAPI で暗号化して保存

信頼性とデータ保全

ログ集約基盤の第一の責務は「ログを失わないこと」である。Yagura は以下の設計によりこれに応える。

  • 規格外メッセージの保全 — 解析に失敗したメッセージも破棄せず、原文のまま「解析失敗」の印を付けて保存する
  • 取りこぼしの可観測性 — 取りこぼしは発生箇所別カウンタで観測でき、CI（継続的インテグレーション）でも検証されている
  • ディスクスプール — 保存先データベースの障害時は受信データをディスクへ退避し、復旧後に取り込む
  • 途絶の検知 — 送信元単位で受信の途絶を検知し（opt-in）、メール通知に連携できる。「気づかぬうちに収集が止まっていた」事態を防ぐ
  • リリースの完全性 — 配布物には checksum（.sha256）が付され、取得物の同一性を検証できる

同梱される Fluent Bit も Apache License 2.0 で提供される。

免責について

Apache License 2.0 の定めにより、本ソフトウェアは「現状のまま（AS IS）」提供され、明示・黙示を問わずいかなる保証も伴わない。導入にあたっては、後述の導入プロセスに沿った自組織での検証を前提とされたい。

コスト構造

ライセンス費用・保守費用は発生しない。導入コストは、既存 Windows サーバ上のリソース（またはサーバの新設）と、導入・運用の人件費のみである。運用に要する技能は Windows サービス・SQL Server・Active Directory の管理といった、Windows 管理者が通常保有するものに限られる。

導入プロセスの推奨

OSS として無保証で提供される性質上、次の段階的な導入を推奨する。

  1. 検証（PoC） — 検証機に MSI を導入し、代表的な機器数台の syslog を受信。解析結果・画面・運用性を確認する（構築手順）。checksum による配布物の検証もこの段階で手順化する
  2. パイロット運用 — 対象機器を広げ、内蔵 SQLite のまま一定期間運用。受信量を実測し、ディスク容量と保持期間を確定する。必要に応じて TLS 受信・アクセス制御等の opt-in 機能を評価する
  3. 本番移行 — 要件に応じて保存先を SQL Server へ昇格し、重要送信元を途絶検知のウォッチリストへ登録、メール通知を有効化する。Windows イベントログの集約もこの段階で展開する

リリース方針（v1.0 基準）

本番推奨版である v1.0 は、期日ではなく、第三者が検証できる次の基準により定められている。基準は事前に固定されており、達成しやすい形へ変更されることはない。

  1. 機能の完備
  2. 独立した二環境 × 連続三十日の実運用実績
  3. 利用者向け文書の完備
  4. 後方互換性の凍結
  5. リリースの完全性（コード署名・checksum 等）

現在の到達状況および最新のリリース内容は GitHub Releases を参照されたい。導入時期の判断（v1.0 到達を待つか、検証を先行するか）の材料として、この基準の透明性をご活用いただきたい。

よくある質問（FAQ）

商用環境（企業の業務システム）で無償のまま利用できますか？
はい。Apache License 2.0 の下で、商用・社内利用・改変を含めライセンス費用なしで利用できます。条文および NOTICE の順守は必要です。
インターネットに接続できない閉域環境でも導入できますか？
MSI は self-contained 形式で、.NET ランタイムの事前導入や導入時のオンライン取得を前提としないため、閉域網への持ち込み導入が可能です。
既存の SQL Server をログ保存先として利用できますか？
はい。導入直後は内蔵 SQLite に保存され、管理画面のウィザードで既存の SQL Server へ切り替えられます。接続パスワードは Windows DPAPI で暗号化して保存されます。
ベンダーによる商用サポートは提供されていますか？
現時点で有償サポート契約は提供していません。GitHub Issues／Discussions によるコミュニティベースの体制であり、ソフトウェアは無保証で提供されます。
閲覧できる利用者を制限できますか？
はい。既定は LAN 内に読み取り専用・無認証で公開されますが、Windows 統合認証 + AD グループによる役割制御（閲覧／管理）と HTTPS 化を設定で有効化できます。
